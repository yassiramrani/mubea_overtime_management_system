1 · What this system is — and what it is not

The confirmed business workflow is approval of overtime in advance — not payment for actual hours worked.

✅ In scope (this release)

  • Advance OT request: submit → approve / reject / withdraw
  • Head-manager review with estimated cost and full audit history
  • HR employee assignment (eligible application accounts)
  • Saved, checksummed review CSV (approval-review-v1) with preview, download and import-result recording
  • Durable email outbox with scheduled delivery command
  • Role-scoped APIs, audit trail, concurrency guards

⛔ Explicitly out of scope (deferred)

  • Direct SAP integration — CSV is a human-reviewed handoff; no import adapter exists
  • Actual-hours / payroll processing
  • Separate personnel directory (assignments use app user accounts)
  • Drafts, amendments of approved requests, cancellation
  • Per-day/per-employee allocations, shifts, breaks, overlap checks
  • SSO, delegated approvers, reminders/escalations, reporting
Unit caveat carried forward total_hours means employee-hours (5 people × 3 h = 15). HR sign-off on this interpretation is required before importing legacy records — existing quantities were not multiplied or reinterpreted.

Transition guards — what makes each step safe

StepEndpointWhoGuardsSide effects
SubmitPOST /api/requests/dept mgr / adminworkflow fields injected into body are rejected; hours ≥ 0.5; end ≥ startpending + audit snapshot + outbox mail
ApprovePATCH …/approve/head / admin, not requesterpending only; empty body; row lock + conditional UPDATE … WHERE version=Napproved + attribution; version +1; mail to HR & requester
RejectPATCH …/reject/head / admin, not requesterpending only; rejection reason required; same lock/version guardrejected + date/reason; version +1; mail to requester
WithdrawPOST …/withdraw/requester onlypending only; reason requiredwithdrawn; version +1
AssignPOST /api/assignments/HR / adminrequest approved; expected_version match; ≥1 unique employee if required; blocked once exportedassignment completed; version +1; mail to requester
Preview exportPOST /api/sap-exports/preview/HR / adminapproved + attribution present; version match; not already exported; assignment complete; every assignee still eligibleread-only CSV text + notice

Record resultPOST …/record_result/HR / adminbatch not already confirmedconfirmed / failed + SAP ref; audit per request
Why the guards matter Concurrency is the core design: PostgreSQL row locks and versioned conditional updates mean two managers racing on the same request (approve vs reject, or export vs export) get exactly one winner and a 409 for the loser — verified by 3 dedicated PostgreSQL tests in CI.
Legacy data gate Approved records lacking approver/date are blocked from export until reconciled against authoritative documents — they must not be silently “fixed”.

5 · Data model — 7 entities

Append-only audit; immutable exports; PROTECT on requester to preserve history.

User + UserProfile

role (dept/head/hr/admin) · department (logistics, quality, production, maintenance, planning) · phone.
Eligible employee = active, non-staff, non-superuser, non-admin.

OvertimeRequest

request_id = OT-<DEPT>-<uuid> · title/description/reason · start/end · total_hours (≥ 0.5) · hourly_rate · estimated_cost computed in save() · approval/rejection fields · version (optimistic lock).
DB check constraints: dates ordered, positive hours, non-negative rate.

EmployeeAssignment 1:1 request

assigned_by · status (pending/completed/cancelled) · M2M assigned_employees · notes.

SAPExport 1:1 request

Freezes an exported request · links to batch · status mirrors import result · SAP reference.

ExportBatch

UUID pk · csv_content · SHA-256 checksum · row_count · format approval-review-v1 · status generated/confirmed/failed · confirmed_by/at.

AuditEvent

Append-only: request · actor + actor_name snapshot · action · JSON details · timestamp. Powers the “history” endpoint and dashboards.

EmailLog (outbox)

recipient · saved subject/text/HTML · email_type · attempts · next_attempt_at (exponential backoff) · delivered_at · status. 5 failed attempts → terminal failure. Queue checks detect failed, stale, exhausted and empty-body rows.

Identity note

Assignments reference application user accounts — no personnel directory / SAP personnel IDs yet (future work).

6 · Delivered scope (what exists today) Phase 1

Workflow & API

  • Explicit audited actions only — generic PUT/PATCH/DELETE on requests & assignments disabled
  • Transactional decisions / assignments / audit / outbox writes
  • Versioned concurrency (409 conflicts) on decide, assign, export
  • Withdrawal with reason; rejection reason required
  • Audit history endpoint with submitted snapshot

Export pipeline

  • Explicit selection with per-request version check (stale queue → refresh)
  • Validation preview before commit; friendly per-request error messages
  • Persisted batch + checksum · immutable confirmed result · authenticated re-download
  • Duplicate export prevention via SAPExport lock
  • CSV formula-injection escaping on text cells (csv_cell)
  • Legacy approvals without attribution stay blocked

Security & access

  • Role scoping at queryset level + permission classes per action
  • Requester can never approve/reject own request
  • Login throttling · 8-hour tokens · server-side logout
  • Injected approval/cost/requester fields rejected on create
  • Workflow & audit models read-only in Django admin
  • Eligibility re-checked at assign and export time
  • Superuser-only account API: Django password validators, deactivation instead of deletion, self- and last-admin lockout guards

Notifications

  • Durable outbox — sending never blocks the request API
  • Bounded retries (5 attempts, exponential backoff)
  • Commands: send_notifications, send_test_email, check_notifications, seed_users, check_legacy_requests
  • Escaped HTML + plain-text snapshots for every notification type
  • Optional test allowlist with TEST / DEMO markers; production delivery defaults to disabled
  • Two verified dev senders: Outlook desktop (Windows) + local capture
  • Demo evidence: 4 captured emails + workflow video in repo

Frontend

  • Login + 4 workspaces (3 role dashboards + admin console), paginated, search/filter/order
  • Administration console: key figures, approval queue, outbox health, department workload, export batches, and superuser account & role management
  • Change password from any workspace header; rotating it signs out the account's other sessions
  • Assignment repair (remove any selected employee), export selection across pages
  • Cost & justification on approval screen; reasons & assigned teams on dept screen
  • Export history with download + import-result recording on HR screen
  • Protected routes wait for auth; relative API URLs + Vite proxy

Verification & ops scaffolding

  • 5 Oct: 88 backend tests run — 85 passed, 3 PostgreSQL-only concurrency tests skipped
  • Historical remote CI on main green on Linux; current Stage 1 changes not checked remotely
  • Playwright browser workflow: dept → head → HR → admin console → account create/deactivate → password rotation (isolated temp DB, fake users, in-memory email)
  • Production settings fail fast; nginx / systemd / backup examples; /health/

10 · Risks & caveats to carry forward

Delivery & mail

  • Outlook sender runs only on Windows with the desktop client signed in — it sends from that person’s mailbox
  • Production settings refuse to start unless SMTP backend selected → no accidental promotion
  • Local mail capture accepts unauthenticated mail — must stay bound to 127.0.0.1
  • Optional test mode marks subject, text and HTML and redirects to an allowlist; use fictional data in a disposable database
  • Production outbox delivery defaults to disabled; sender verification remains available before activation
  • Queue monitoring detects failed/stale/stuck rows; real alert routing and scheduler installation still pending
  • Delivery is at-least-once: crash between SMTP acceptance and DB commit can duplicate a notification (business actions remain deduplicated)

Data, SAP & operations

  • No real SMTP authentication tested; no production deployment performed or verified
  • No SAP import adapter — CSV is review-format only; “import confirmed” is human-recorded
  • Approved requests are intentionally immutable — corrections need the future amendment workflow, not DB edits
  • Legacy quantities not reinterpreted; reconciliation required before export
  • Database operators remain privileged — need controlled access + backups
“SAP contract” open questions — ask the SAP team for an accepted advance-authorization sample 1) Required personnel/department/cost-center/overtime-type IDs · 2) Are unnamed department authorizations accepted? · 3) Do rows represent request, employee, date, or shift? · 4) Meaning of hours, currency, rate, time-zone boundaries · 5) Encoding, separators, decimal/date formats, column order, max lengths, validation · 6) Import errors, partial acceptance, corrections, dedup identifiers. A final machine-import adapter must implement the SAP contract — it must not blindly reuse the review-file CSV transformations.
Upgrade / migration path (existing installation) Stop writes → keep old release + tested backup → check_legacy_requests (read-only preflight) → migrate → deploy backend + frontend together (assignments now require expected_version; exports require explicit request_ids + versions; re-download uses saved-batch endpoint). Do not reset or delete existing data.
